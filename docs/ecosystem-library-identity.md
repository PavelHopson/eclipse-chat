# Identity-клиенты Eclipse

Кандидат 2026-11-07. Не опубликован и не включён на сервере.

Существующий DnD-клиент и ECOSYSTEM_IDENTITY_REDIRECT_URIS сохраняются. Дополнительные клиенты подключаются явно через ECOSYSTEM_IDENTITY_CLIENTS_JSON: массив объектов id/redirectUris, не более 16 клиентов и 8 точных URI на клиента. Повторные id, перезапись DnD и небезопасные URI отклоняются при запуске. Audience равен id клиента, произвольный audience не принимается.

Первый клиент:

```json
[{"id":"eclipse-library","sessions":true,"redirectUris":["https://library.eclipse-forge.ru/editor-api/api/editor/identity/callback"]}]
```

Без настройки Library получает invalid_client. Коды одноразовые, связаны с PKCE S256, clientId и точным redirectUri. Identity assertion подтверждает только sub/name, не роль редактора. Владелец Chat не получает права на другие продукты автоматически.

Экран #authorize поддерживает названия Library и остальных основных Eclipse-проектов. Наличие названия не включает клиент: backend отдельно проверяет серверную регистрацию. Для следующего проекта нужны собственный callback, audience и проверка локальных прав в backend проекта. Сервисные ключи AI Hub и локальные токены Media/Sentinel не передавать в браузер.

Перед публикацией проверить стандартные CI и совместимость действующего DnD-входа. Новая конфигурация не устанавливалась, production-вход не проверялся. Настройку серверной среды включить в штатный deploy, не выводить значение ключа подписи в журналы.

## Длительные сессии и общий выход

Для `sessions:true` обязательны миграция `20261107120000_ecosystem_sessions` и `AUTH_PROTOCOL_V2_REQUIRED=true`. Предварительно проверить совместимость установленных desktop/mobile клиентов с v2. Этот кандидат не меняет серверные флаги. DnD без `sessions:true` сохраняет прежний короткий identity assertion.

Одноразовый код связывается с проверенным sid Chat. После обмена сервер выдаёт отдельный случайный grant максимум на 8 часов и не дольше родительской RefreshToken-сессии. В БД только его SHA-256; FK каскадно удаляет grants при отзыве родителя. Ротация refresh-токена сохраняет sid. Максимум 32 активных grant на клиент/сессию; просроченные очищаются при следующей выдаче. Привязка аккаунта также расходует grant; после окончания привязки он не используется и истекает в течение 8 часов.

`POST /api/ecosystem/session/inspect` и `/revoke` принимают только `{clientId,token}`; sid пользователя не принимается. Операции требуют серверный grant, не короткий assertion. Неверный clientId не позволяет отозвать чужую сессию. Revoke идемпотентен и отключает socket-соединения связанной сессии. Library проверяет inspect для каждого действия и не разрешает операции при 503. Право редактора принадлежит только Library.

Включать по порядку: миграция Chat → backend Chat → проверка v2 → клиент Library в конфигурации → schema.sql Library → API Library с отдельным ключом шифрования → frontend → реальный вход владельца и проверка выхода. Не включать остальные продукты одним списком: они ещё не реализовали проверку grants.

## Совместимость клиентов — 2026-11-07

Текущий web-код отправляет X-Eclipse-Auth-Protocol: 2 для login/register/refresh и авторизованных API, Socket.IO использует protocol: 2. Desktop Tauri и Android Capacitor в текущем checkout загружают общий удалённый web URL; отдельного встроенного auth-клиента у них нет. На компьютере найден установленный Desktop 1.0.10, однако его фактический WebView и сессия на production не проверялись. Старые закэшированные интерфейсы и старые системные WebView остаются отдельным риском выпуска.

Воспроизводимая проверка: Node 24+, установленный playwright через PLAYWRIGHT_MODULE, затем `node deploy/scripts/identity-client-browser-smoke.mjs`. Проверяются настоящие модули api/storage/accountVault в Chromium, серверные ответы моделируются. 5 сценариев PASS: legacy-session upgrade, запрет повторной отправки мутации, отзыв сессии, блокировка старого клиента, одна ротация при двух параллельных запросах. Новых зависимостей тест не добавляет. Это не замена проверки установленного Android/Desktop и реального сервера.

Безопасный выпуск: сначала код/миграции с SSO выключенным, затем проверка актуального интерфейса и сессий на установленных клиентах. Только после этого включать требование v2 и Library SSO. При несовместимом клиенте остановить включение, обновить клиент, не ослаблять серверную проверку ради доступа.
