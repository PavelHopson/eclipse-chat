Задачи реестра: 00-010, 30-009, 40-007, 00-102 (часть 00-028).
Это план ручной приёмки на 10–15 минут и разбор кода. Слышимость автотестами

## Подготовка (2 мин)

| Клиент | Что записать до старта |
| --- | --- |
| **A — Windows-приложение (Tauri, WebView2)** | версия Chat внизу настроек; версия WebView2: `edge://version` недоступен — смотреть «Параметры Windows → Приложения → Microsoft Edge WebView2 Runtime»; модель гарнитуры/колонок |
| **B — web, Chrome/Edge на втором ПК** | `chrome://version` (первая строка); `GET /eclipse-chat/api/version` |
| **C — Android-приложение** | версия APK (настройки → О приложении), версия Android, модель |

- Два разных аккаунта (A и B), оба участники одного тестового сервера; голосовой канал без посторонних.
- На A и B заранее открыть DevTools-консоль (в Tauri — правый клик → «Проверить», если включено; иначе пропустить) и фильтр `livekit|voice|audio`.
- Если пункт падает — записать: время, клиент, шаг, текст ошибки в UI, 20 строк консоли, скриншот. Не продолжать «вслепую» на сломанном шаге — следующий пункт с чистого входа в канал.

## Подозрения по коду

Код: `apps/web/src/hooks/useVoice.ts` (`SCREEN_SHARE_CAPTURE_OPTIONS`,
`toggleScreenShare`, `TrackSubscribed`, `applyRemoteAudioState`).

**S1 — главная причина «второй участник не слышит звук экрана в WebView2».**
`SCREEN_SHARE_CAPTURE_OPTIONS` просит `video: { displaySurface: "window" }`
(с v1.7.79, чтобы пикер открывался на окнах, а не на «только своя вкладка»).
Chromium — и, значит, WebView2 — на Windows захватывает звук только у
**вкладки** (звук вкладки) и у **всего экрана** (системный loopback).
У захвата **окна** аудиодорожки нет: галочки звука в пикере нет,
LiveKit публикует только `screen_share` без `screen_share_audio`, зрителю
нечего воспроизводить. Это подтверждено и в нашем браузерном smoke
(`screen-source-picker-2026-10-15.md`: «fixture window без audio — только
screen video»). Ошибки в коде нет, есть ограничение платформы, которое UI
сейчас не объясняет.
Варианты (решение Павла, кодом не правил — см. «Почему без правки»):
1. Короткий текст в UI после старта: если публикации `screen_share_audio`
   нет — «Звук окна не передаётся. Чтобы зрители слышали звук, выберите
   «Весь экран» и включите «Поделиться системным звуком»».
2. Звук именно окна в Windows-приложении — только нативно (WASAPI process
   loopback, Windows 10 2004+) через Tauri-команду и отдельный LiveKit
   audio track. Это отдельный срез с security-review.
3. Проверить в актуальном WebView2 новую опцию `windowAudio` у
   `getDisplayMedia` (в Chromium появилась экспериментально; поддержку в
   установленной версии не подтверждал — только после ручной проверки).

**S2 — эхо при «Весь экран + системный звук».** Системный loopback
захватывает всё, что играет на ПК, включая голоса собеседников из самого
звонка; `echoCancellation: false` для экрана (сделано ради качества
музыки) это не гасит. Итог: собеседники слышат себя с задержкой через
трансляцию A. Возможное смягчение — `restrictOwnAudio` / наушники у
транслирующего; проверить п.6.

**S3 — громкость трансляции не отделена от голоса.** Remote-аудио ключуется
`participantIdentity`; `applyRemoteAudioState` применяет одну громкость и
одно «заглушить» ко всем дорожкам участника — микрофону и
`screen_share_audio`. Отдельного ползунка «звук трансляции» нет. Это не
причина тишины, но объясняет жалобы «убавил человека — пропал фильм».

**S4 — autoplay.** Звук может молча блокироваться автоплеем (особенно
после переподключения или если вход в канал был не по клику). Код это
обрабатывает: `AudioPlaybackStatusChanged` + кнопка восстановления. В п.1
и п.9 записывать, появлялась ли кнопка.

**S5 — Android.** Приложение — Capacitor WebView с удалённым фронтом;
Android WebView не реализует `getDisplayMedia`, поэтому демонстрация с
телефона недоступна. Приём звука/видео работает штатно.

**Почему без правки кода.** S1 — ограничение платформы, «явного» бага в
нашем коде нет; варианты 1–3 меняют UX/нативный слой и требуют решения.
Кроме того, `useVoice.ts` и `VoiceRoom.tsx` сейчас содержат
незакоммиченную работу в основной папке репозитория — параллельная правка
дала бы конфликт.

## Решение 25.11: делаем оба варианта

### A — подсказка в интерфейсе (сделано в этом срезе)

`VoiceRoom.tsx`: прежний общий текст «трансляция без звука» заменён
адресной подсказкой (`screenShareAudioHint`). Поверхность берётся из
`MediaStreamTrack.getSettings().displaySurface` локальной демонстрации,
платформа — из `navigator.userAgentData.platform`:
- Windows + окно → «Звук отдельного окна не передаётся… выберите «Весь
  экран» и включите «Поделиться системным звуком»» + совет про наушники (S2);
- Windows + весь экран без галочки → включить системный звук;
- вкладка → «Поделиться звуком вкладки»;
- прочее (macOS/Linux, неизвестно) → вкладка браузера; «весь экран» не
  обещаем — системного loopback там нет.
`useVoice.ts` не менялся. Тест — `deploy/scripts/voice-room-ui.test.mjs`.

### B — нативный захват звука окна в Windows-приложении: план (не начато)

**Технология.** WASAPI process loopback (Windows 10 2004 / build 19041+):
`ActivateAudioInterfaceAsync(VIRTUAL_AUDIO_DEVICE_PROCESS_LOOPBACK)` с
`AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS { TargetProcessId,
PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE }` через crate `windows`.
Захватывается звук только выбранного процесса (и его дочерних), поэтому
голоса звонка в трансляцию не попадают — S2 (эхо) решается тоже.

**Как узнать, какое окно выбрано.** Chromium не отдаёт странице HWND/PID
выбранного окна. Поэтому: после старта видео нативная команда
`window_audio_candidates` перечисляет процессы с активными аудиосессиями
(`IAudioSessionManager2`) и предлагает совпадение по заголовку окна
(`track.label` ↔ `EnumWindows`); пользователь явно подтверждает источник
звука. Это второй, отдельный акт согласия — не автозахват.

**Транспорт.** Rust-поток захвата → 10 мс кадры f32 48 кГц stereo →
`tauri::ipc::Channel` (бинарно, ≈ 384 КБ/с) → AudioWorklet с кольцевым
буфером → `MediaStreamAudioDestinationNode` → LiveKit `LocalAudioTrack`,
опубликованный как `Track.Source.ScreenShareAudio`. Зрителям ничего менять
не нужно: приём `screen_share_audio` уже есть.

**Объём.**

| --- | --- | --- |
| Спайк: запись 10 с звука процесса в WAV по PID на ПК Павла | `apps/desktop/src-tauri/src/window_audio.rs` (новый) | 1 день |

Итого ≈ 4–5 дней. Нужен **новый нативный релиз** Windows-приложения
(установщик + подписанное автообновление), веб-обновления недостаточно.

**Риски.**
- *Безопасность (главный).* Фронт приложения удалённый
  (`app.star-crm.ru`), значит XSS на сайте = возможность слушать звук любой
  программы. Меры: команда только по жесту пользователя во время активной
  демонстрации, нативный диалог подтверждения с именем процесса на каждый
  старт, видимый индикатор в трее, автостоп при выходе из звонка и
  остановке видео, capability только на три команды. Нужен
  security-review.
- *Совместимость.* Windows < 19041 — не работает (оставляем подсказку A).
  Защищённые аудиопотоки (DRM) и некоторые игры с эксклюзивным режимом
  могут давать тишину.
- *Синхронизация.* Задержка аудио относительно видео (буфер + IPC) — цель
  < 100 мс, проверить вручную.
- *Сопровождение.* COM/unsafe-код в Rust, тестируется только на Windows.

**Где незакоммиченная работа Кодекса.** Основная папка
`E:\projects\eclipse-chat` стоит на `2bf5f14` (5 сентября), на 50 коммитов
позади `origin/master`. Незакоммиченные правки: `useVoice.ts` (+326/−61),
`VoiceRoom.tsx` (+76), `AudioPlayer.tsx`, `VoiceRoom`-стили, настройки и
др. По содержимому это сентябрьская работа над звуком демонстрации и
громкостью, которая в основном уже вошла в master (релиз 1.7.74). Срез B
трогает `useVoice.ts` только в одной точке (`toggleScreenShare`), остальное —
новые файлы; черновик Кодекса не трогаем, перед стартом B стоит решить, что
из него ещё актуально.
